### A4 ❗ 同名 `det` 有两套实现，行为不一致（2026-10-04 补测试时发现）

- **量法**：`grep -rn "export function det" src/core/*.ts`
- 实测两处：

  | 位置 | 非方阵（如 2×3）时 |
  | --- | --- |
  | `src/core/linalg.ts:136` | `detSmall` 只索引 `[0][0] [0][1] [1][0] [1][1]` ⇒ **静默丢弃多余的列**，得 -3 |
  | `src/core/machine.ts:473` | 现有 `machine.test.ts` 断言它**返回 NaN** |

  同名、同一个数学操作、**两种答案**。方阵时两者应当一致（未逐例比对，本轮没查）。

- **怎么发现的**：给 `linalg.det` 写测试时，我断言"非方阵应为 0"，
  跑出来是 -3；去 `machine.ts` 找依据，发现那边的既有测试明写"非方阵给 NaN"。
  **既有测试与新测试对撞才暴露出来，单看任一处都发现不了。**

- 现状处置：`linalg.det` 那条测试**刻意钉现状**（得 -3、且等于对前 2×2 求 det），
  而**不是**改成 0 或抛错 —— 改行为属产品决定，不该由测试单方面定。
  测试注释与本条都标注了「现状刻画，不是认可」，
  这样下一个人改动它时会被立刻看见。

- ✅ **订正（2026-10-19 实测补齐，原文此处是「⚠️ 没量到」）**：
  - **量法**：`linalg.det`（闭式 / LU）与 `machine.det`（高斯消元）各跑 **16 000 组**随机方阵
    + **36 组**近奇异 + 边界输入；`inv` / `solve` / `mulMat` 同法。
  - **方阵上两者数学等价**：显著差异 **0 组**，最大绝对差 **3e-13**；
    最大相对差 **25.6%** 出现在 det ≈ 0 的抵消场景（分母趋零，不是实现缺陷）。
  - **边界上分歧**（这就是**不能整体合并**的原因）：

    | 场景 | `linalg` | `machine` |
    |---|---|---|
    | 非方阵（3 行 2 列） | 静默取前 n×n 块 ⇒ **-3** | **NaN** |
    | `inverse([])` | `[]` | `null` |
    | `solve` 的 b 长度不对 | **抛错** | 返回 **NaN 数组**（truthy ⇒ `if (!sol)` 判不出） |
    | `inv` 近奇异（36 组） | — | **2 组分歧** |
    | `matMul` 遇 `0 × NaN` | 「跳过零项」优化 ⇒ 与逐元素算不同 | 逐元素算 |

  - **处置**：**不合并**（05 的 `M-13` 未落地）—— 合并会改变**可观察行为**，
    前提是**先统一错误策略**，属产品决定。
  - **替代交付**：`tests/linearAlgebraContract.test.ts`（11 条）把两套实现的
    **契约关系**写成可执行断言（方阵一致 + 边界分歧逐条列出 + 「合并的前提是先统一错误策略」）。
  - **一条反直觉的实测**：`linalg.det` 的「3×3 改走 LU 分解」看起来语义等价，
    实测**不等价** —— `r <= 3` 这个门槛同时决定了**非方阵**的行为
    （走 `detSmall` 时 `a[2][2]` 是 `undefined` ⇒ NaN）。变异验证里它**咬住了**。

## E. 本轮（2026-10-19）新查出来的东西

### E1 ❗ 既有测试里一处**真断言缺陷**（已修）

- **量法**：把 `tsconfig.json` 的 `include` 纳入 `tests/` 后跑 `npm run typecheck`，
  暴露出 **52 条**既存类型错（44 × TS2554 helper 少 `msg` 参数、6 × TS2345 `evThrows` 签名、
  2 × TS6133），其中 `machine.test.ts` 的一处是**断言本身写错**：

      assert.equal(actual, expected, 1e-12, msg)

  `assert.equal` 只有 **3** 个参数（actual, expected, message）⇒ `1e-12` **落到了「消息」位**，
  真正的 `msg` 被丢弃，而且这条断言是**严格相等**（容差根本没生效）。
- **处置**：换成带容差的 `near` 辅助函数。
- **顺带**：`tsconfig` 纳入 `tests/` 之后，`npm run typecheck` 才真正覆盖测试代码
  （此前 `include` 只有 `["src","scripts"]`）—— CI 的 typecheck 门禁**一直漏着测试代码**。

### E2 ✅ 变异反向验证：判据必须证明自己咬得住

- **量法**：逐条把被测源码改成错的（精确字符串替换）→ 跑 `npm test` → 记录 → **内存字节快照还原** + `sha256` 核对。
- **实测**：**33 条**变异，**32 条咬住**（有测试失败），**1 条语义等价**
  （把 worker 采样区间高度 `y+dy` 改成 `y`：`domainColor(..., h=1)` 只用第 0 行，高度不参与计算）。
- **两条首轮不咬住的，根因都是判据问题**（不是实现问题）：
  1. RK4 收敛阶测试用的 `y' = y` 是**自治**场 ⇒ rhs 不看 t ⇒ 「k2 的时间点写错」对它无影响。
     ⇒ 改用非自治场 `y' = t + y`（解析解 `e^t − t − 1`，实测误差比 15.35 / 15.67 ≈ 2⁴）。
  2. rasterPool 只断言了「带**铺满** `[0,h)`」⇒ 带大小改一半仍铺满 ⇒ 判据不敏感。
     ⇒ 补判据「每条带行数 = `ceil(h/(WORKERS×BANDS_EACH))`（末带为余数带）」。
- **一条被实测纠正的「疑似缺陷」**：初测时用「等值线两侧场值符号必须相反」判 marching squares
  歧义构型的连通方式，4/4 条线段被判「同号」⇒ 看着像连错了。
  查下去发现**判据本身错了**（双曲线弧被线性插值成**弦**之后，弦两侧本来就可能同号）。
  改用**标准「格心均值」消解规则**重算 ⇒ **实现完全正确，没有缺陷**。

### E3 ✅ 数值梯度校验（`nn.ts`）

- **量法**：中心差分（ε=1e-6）逐参数对比 `sampleGrad` 解析梯度
- **实测**：22 个参数，**最大绝对误差 1.5e-10**；tanh / relu / sigmoid 三种激活各测一遍。
- **为什么这条重要**：激活函数导数写错、梯度方向写反、softmax 归一化漏掉，
  都不会抛错，只会让「训练到 98%」永远训不上去 —— 属于**静默失败**。
